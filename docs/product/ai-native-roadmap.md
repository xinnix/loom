# AI 原生框架推进路线图

> 2026-10-13 评估定稿。本文档回答两个问题：Loom 相对「AI 时代的原生开发框架」这一目标处在什么位置；接下来按什么顺序补齐。执行明细仍走 [backlog.md](backlog.md)（epic）→ [task/](../task/README.md)（任务），本文档只记方向、顺序与判定依据，不重复条目。

## 定位：两条线

Loom 的「AI 原生」由两条互补的线构成，评估与推进分开衡量：

| 线                                   | 含义                                              | 载体                                                         |
| ------------------------------------ | ------------------------------------------------- | ------------------------------------------------------------ |
| **线 1：AI 替人写代码**（开发时 AI） | AI Agent 按固定模式完成全栈开发，人只做建模与审查 | `.claude/skills` 体系、genModule、抽象层三件套、治理规则     |
| **线 2：产品里跑 AI**（运行时 AI）   | 框架原生承载 AI 能力，派生项目的业务直接调用      | AI 三层架构（ADR-005：LLM 配置 / YML 工具 / YML Agent 编排） |

两线在 genModule 汇合：生成器最终也能产出模块的 AI 能力（YML 工具声明、Agent 定义随模块生成）。到那时，框架才配称「AI 时代的原生开发框架」。

## 现状快照（2026-10-13）

| 线   | 完成度 | 依据                                                                                                                                                                               |
| ---- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 线 1 | ~60%   | M1/M2 扎实（核心特性、抽象层、标准化、治理）；skill 体系 20+；**缺**：E1 E2E、E2 strict、E4 全端生成                                                                               |
| 线 2 | ~25%   | ADR-005 骨架完整（加密/YML 编排/SSE/AgentRun 审计/Playground）；**但**均为「单 Agent + 只读工具 + HTTP 生命周期内短任务」：无会话记忆、无写操作、无异步/定时、无用户端消费、无 RAG |

关键教训（2026-10-13）：AI 三层架构交付当晚测试全绿，次日实测连踩 4 个缺陷（dev 加载、渲染死循环、接口裸奔、LLM 调用全挂），全部落在单元测试盲区（真实进程 / 真实浏览器 / 真实编译产物）。**结论：E1 不是普通工程债，是线 1 的质量闭环地基**——AI 大量生成代码的前提是生成物可被自动验证。

## 推进顺序

五步。1-2 收尾 M3（线 1），3-4 是线 2 的第一批纵深，5 立项评估。

| #     | 步骤                      | 做什么                                                                                       | 为什么是这个位置                                                                                           |
| ----- | ------------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **1** | **E1 测试体系（最小版）** | Playwright E2E 主路径（Admin CRUD、Web 登录→Todo）；API 集成测试跑真实 PostgreSQL            | 今天刚被验证的最大杠杆；后续所有 AI 生成代码都靠它兜底                                                     |
| **2** | **E4 + E2 收尾 M3**       | genModule 全端输出（Web REST + 页面、miniapp 页面）；API/Admin 开启 TS strict，消除 `as any` | 线 1 的覆盖面与类型闭环；strict 是 AI 生成代码的第二道自动验证                                             |
| **3** | **运行时 AI 第一批**      | ①用户端 REST 消费（User 身份的 Agent 执行路径，工具转发带用户 JWT）②会话/多轮记忆持久化      | 把 AI 从 Admin 内置变成全端能力——「原生框架」与「Admin 玩具」的分水岭；走 R4 边界（外部端 REST），不破红线 |
| **4** | **写操作工具 + 审批链**   | 工具突破只读边界；human-in-the-loop 审批流（ADR-005 已预留）                                 | 业务系统迟早要 Agent 写库；审批链是安全阀，与 RBAC 天然契合                                                |
| **5** | **智能密度评估立项**      | RAG/向量库、多 Agent 协作、evals 评估、模型路由/fallback、成本报表                           | 高频需求但依赖前四层的底座；独立 epic 评估后立项                                                           |

## 边界与原则

- 顺序可按派生项目实际需求微调，但 **1 必须最先**，且任何一步不得破坏 [vision.md](vision.md) 红线（R1-R7）
- 线 2 每步落地时先补/改 ADR（运行时决策密度高），YML 契约变更走 `infra/shared` 契约层
- MVP 边界逐批打开：每批打开什么、明确不做什么，写进对应 ADR 的「MVP 边界」节

## 维护

- 定位与完成度快照每季度复核一次（或重大交付后）
