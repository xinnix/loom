# Task — 任务追踪系统

## Overview

在 `docs/task/` 目录下维护一套持久化的任务文档，Agent 在开发全生命周期自动读写。实现：

- **跨会话上下文恢复** — 清空上下文后，读取 `active/` 下的文档即可接续
- **进度可视化** — 通过 `README.md` 看板一览所有任务状态
- **Git 追踪** — 文档随代码提交，团队共享，不依赖个人环境

## Directory Structure

```
docs/task/
├── README.md           # 任务看板 — 集中索引所有任务
├── TEMPLATE.md         # 任务文档模板（首次使用前阅读）
├── active/             # 当前进行中的任务
│   └── {feature-name}.md
└── completed/          # 已完成的任务存档
    └── {feature-name}.md
```

## When to Use

| 场景           | 触发条件                                                               |
| -------------- | ---------------------------------------------------------------------- |
| **开始新功能** | 用户要求开发一个新特性、修复 bug、或做任何需多步完成的工作             |
| **检查进度**   | 用户问「做到哪了」「有什么任务在进行」— 先读 README，再读 active 内容  |
| **更新进度**   | 完成一个子步骤、遇到阻塞或决策点                                       |
| **完成功能**   | 整个功能开发完毕，关闭任务                                             |
| **恢复上下文** | 新会话开始，或用户说「之前做到哪了」— 先读 README + active/ 下所有文件 |

## Instructions

### 1. 开始新任务

当用户要求开始一个新功能/修复/变更时，在你开始编码**之前**：

1. **检查 `docs/task/README.md`** — 看是否有冲突的进行中任务
2. **用 TEMPLATE.md 创建新文件**：`docs/task/active/{简短特征名}.md`
   - 文件名用短横线小写，如 `add-user-login.md`
   - 填写「目标」「检查清单」（分解为可勾选的步骤）
   - 「当前状态」写初始描述
3. **更新 `docs/task/README.md`**：在「进行中」表格追加一行

> **注意**：第 2~3 步应在开始写代码前完成，先建立任务再行动。

### 2. 更新任务进度

在开发过程中，每完成一个逻辑步骤：

1. **勾选检查清单**：将 `[ ]` 改为 `[x]`
2. **更新「当前状态」**：说明做到哪、卡在哪、下一步是什么
3. **更新「变更文件清单」**：每新增/修改/删除一个文件就追加记录
   - 格式：`| 路径 | 新增/修改/删除 | 原因简述 |`

「当前状态」是**上下文恢复的核心字段**，必须用人类可读的自然语句描述：

```markdown
> **做到哪了：** 完成了用户表的创建和 JWT 签发，正在进行登录页 UI
> **卡在哪：** 微信登录的回调 URL 需要运维配置后才能调试
> **下一步：** 先完成邮箱密码登录的前端表单
> **决策上下文：** Token 存 httpOnly Cookie 而非 localStorage，SSR 友好且防 XSS
```

### 3. 恢复上下文（新会话）

当这是新会话（或用户问「之前做到哪了」）：

1. **读取 `docs/task/README.md`** — 了解当前有哪些任务
2. **读取 `docs/task/active/` 下所有文件** — 深入了解每个任务的「当前状态」「检查清单」「变更文件」
3. **向用户汇报**：当前进行中的任务、进度摘要、下一步要做什么
4. 继续编码前确认用户是否需要调整优先级

### 4. 完成任务

当检查清单全部勾选、功能可验证时：

1. 将文件从 `active/` 移到 `completed/`：
   ```bash
   mv docs/task/active/{file}.md docs/task/completed/{file}.md
   ```
2. 更新文件头部的状态：`- **状态**：`active`|`completed``
3. **更新 `docs/task/README.md`**：
   - 从「进行中」表格移除该行
   - 在「已完成」表格追加一行
4. **可选**：如有后续任务（如用户说"下一个做 X"），在 README 或新任务中注明关联

### 5. 暂停/终止任务

如果用户中途切换任务，或被要求暂时搁置：

1. 将状态改为 `paused`
2. 在「当前状态」中标注暂停节点和原因
3. 在 README 中保留在「进行中」表格（状态列可标注「暂停」）
4. 开始新任务时重新创建文件

## 任务文档规范

### 文件名

```
{简短英文特征名}.md
```

使用双字节时间前缀**仅当一天内有多个同域任务**：

```
2026-07-13-fix-login-bug.md
```

### 检查清单编写原则

- 每个子步骤应是一个**可独立验证**的单元
- 避免过于笼统（「实现登录」，拆为「建表→接口→前端表单→联调」）
- 避免过于琐碎（「安装依赖」「重启服务」没必要写进去）

### 变更文件清单原则

- 只记对功能有意义的文件变更（新增 service、修改 schema 等）
- 不需要记自动生成的文件、配置文件格式化、纯重构改名
- 每行格式：`| path | 新增/修改/删除 | 原因 |`
